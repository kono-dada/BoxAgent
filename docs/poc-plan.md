这是一份基于当前工作区的 **BoxAgent 桌宠 POC 实施草案**，整理于 2026-09-14。后续已按用户确认实施第 1、2 步，并改为 uv 直接启动；具体状态见 [实现说明](poc-implementation.md) 与 [验收记录](poc-verification.md)。现另已接入第 3 步中的独立窗口摘要演示，但尚无专注委托、云端判断、时间线或长期记忆。下面原样保留当时规划；其中计算器限定、有限任务入口、SQLite、事件字段与视觉参数等不是当前实现规范。

目标是在这台 MacBook 上尽早体验一条完整链路：唤起桌宠说话 → 立即获得反馈 → 后台实际执行或读屏 → 桌宠呈现状态并报告结果 → 启动一个专注委托，由后续事件触发提醒。随后补充本次运行的活动回顾和少量明确偏好。

**当前可以直接复用三个预实验。** 这次不重新开展技术选型，也不把原始实验脚本全部推倒重写。

本次复核了 Computer Use 的原始日志：`20260914-124144` 为 15 次工具调用、47.309 秒；较新的 `20260914-124351` 为 25 次调用、84.049 秒，模型发现错误输入后重新操作，最终也通过。这是包含启动与纠错的两次样本，不是稳定性能指标。它说明首版必须让后台任务独立运行，用户能够看到进度并继续对话。

**建议继续使用 Python + uv，桌面层使用 PyObjC 调用 AppKit。** 这是基于现有代码的 POC 选择：语音、视觉、Computer Use 都已有 Python 路径；PyObjC 提供 macOS 系统框架绑定，也有[透明窗口示例](https://pyobjc.readthedocs.io/en/latest/examples/Cocoa/AppKit/RoundTransparentWindow/index.html)。原生 Swift 迁移可在体验明确后单独决定。

主线程只负责 AppKit 窗口与输入；后台线程运行 asyncio，承接网络与任务；MLX 推理放在独立 Python 子进程，避免推理阻塞语音；Codex 沿用 `.runtime/codex-0.153.0/` 内已经验证的主程序及配套 host。进程在实际需要时启动并复用，退出 POC 时清理。这里不引入 HTTP 服务、Node 前端或通用多 Agent 编排库。

依赖整理属于整合工作：目前语音脚本通过 uv 的脚本依赖运行，视觉使用项目 `.venv`。本次读取 `.venv` 发现没有 PyAudio，且安装的 websockets 为 17.1，与语音脚本的 `<17` 声明不同，因此不能直接把三个入口放进当前环境就视作统一完成。先保存现有可复跑入口，再用 uv 声明主程序依赖；若视觉依赖冲突，保留视觉子进程的独立环境。

**按四个可体验节点实施，每个节点完成后都能直接运行。**

| 顺序 | 用户获得的体验 | 主要工作 | 完成条件 |
| --- | --- | --- | --- |
| 1. 桌宠能聊天 | 快捷键开启／关闭麦克风；角色有待机、听、说等状态；字幕可查看 | 薄窗口、临时角色图形、语音适配、统一启动入口 | 在普通 Terminal 启动，用户能直接和桌宠对话、插话、关闭麦克风；界面不抢工作窗口焦点 |
| 2. 桌宠能派活 | 说“用计算器算一下 137+248”；先获得回应，随后看到后台状态并听到真实结果；可以继续聊天或取消任务 | 将语音工具接到后台 Luna；抽出动态工具转接；接上授权和任务状态 | 结果来自真实计算器；等待不冻结语音或 UI；取消后停止派发后续动作；失败能够显示 |
| 3. 桌宠能看屏并履行一个委托 | 问“我现在在看什么”；说“接下来专注十分钟，浏览无关娱乐时提醒我”；之后可暂停或结束 | 按需截图、常驻视觉 worker、一个专注处理模块、计时事件、独立判断提示词、提醒输出 | 用户消息、计时器、屏幕观察、后台结果都进入同一事件入口；委托生效后能够触发提醒，恢复学习或取消后旧提醒失效 |
| 4. 桌宠能回顾并保留明确设置 | 问“刚才这段时间做了什么”；设置“这次专注只用气泡提醒”等范围明确的偏好 | 记录实际采集的活动区间、查询并总结、保存少量明确设置 | 从 POC 开始采集的记录能按时间回顾；空白不补写；临时设置与长期设置分开，长期设置重启后保留 |

第 2 个节点就是第一个可体验的整合版本；第 3 个节点开始体现本项目的事件驱动特点；第 4 个节点完成最小的持续使用闭环。每个节点里的真人体验、权限适配和错误处理随整合完成，不再拆成新的前置预实验。

音乐属于第 2 个节点之后的同接口扩展：选择一个音乐 App，补齐目标应用范围和实际播放状态核验。当前只有计算器的真实操作得到验证，因此音乐兼容性不作为首个整合版本的阻塞条件，也不提前宣称支持。

**最小运行结构只保留清晰的分工。**

```text
快捷键／麦克风 ↔ 千问语音 ↔ 有限的任务入口
                               ↓
窗口变化／定时检查 → 观察结果 → 事件入口 → 专注处理／任务状态
                               ↓                 ↓
                         桌宠与语音输出      Codex 后台执行
                               ↑                 ↓
                               └──── 进度与结果事件

屏幕解读：截图 → 本地 MLX 子进程 → 带时间和页面身份的文字证据
持久记录：SQLite 保存事件、任务记录和明确设置；截图仅以文件引用关联
```

千问负责听说、理解简单请求并调用有限入口；Codex 后台模型负责多步骤操作，以及需要较强推理的判断；本地 0.8B 模型先只提供屏幕证据。专注判断使用自己的提示词和状态，不放进语音人格提示词，不让它改动计算器的执行规则。

| 新增位置 | 职责与复用来源 |
| --- | --- |
| `boxagent/__main__.py` | 装配并启动桌宠，统一管理退出 |
| `boxagent/desktop.py` | 透明窗口、角色状态、字幕、快捷键、授权展示 |
| `boxagent/voice.py` | 从 `voice-demo.py` 提取会话与音频逻辑；统一处理语音输出请求 |
| `boxagent/runtime.py` | 事件路由、任务句柄、取消标记、输出排队；普通程序逻辑 |

| `boxagent/vision_worker.py` | 加载一次本地权重，串行处理最新图像请求 |

| `boxagent/history.py` | SQLite 记录与时间区间查询、明确设置的读写 |

`scripts/` 和现有证据先保留可复跑能力。直接调用原始执行器的失败入口、历史 Node 对照与诊断代码不成为 POC 的运行依赖。

**事件机制做到足够支撑这些场景即可。** 使用 asyncio 队列和显式处理函数；事件保存 `id`、`type`、`occurred_at`、`received_at`、可选 `task_id`、`scene_revision` 和载荷。先接用户请求、工具进度／结果、屏幕观察、计时器与取消这几类来源。音频包走专用流，图片不塞进事件日志。

任务先支持接受、运行、待授权、完成、失败、取消请求与已停止几个状态。同一应用的界面操作串行执行；收到取消先阻止后续动作，再尝试停止当前模型 turn。已经发出的动作不承诺回滚。任务取消与用户插话清空语音是两件事。

所有主动发声和后台结果通过一个输出入口进入语音会话，避免多个模块同时触发回复。用户正在讲话时保存待回传结果，等待合适的会话状态；发送前检查任务是否仍有效。具体如何关联 Qwen 的 `call_id`、当前 response 和跨轮结果，在节点 2 中结合现有结果回传协议完成；这部分目前尚未接好，不能靠提示词代替。

模型开始生成语音与用户实际听到语音应分开看。角色的说话状态以客户端实际播放状态为准；耗时任务的接受状态由本地任务记录确认；不能把尚未完成的操作报成成功。

**视觉先按需，监控只在委托开启时启动。** 初始使用窗口变化加约 20 秒的定时检查，复用同一个观察接口；截图内容未变时跳过重复推理。1280 像素长边可作为初始配置，需要读小字时提高分辨率；现有单次样本不能证明它是通用最佳尺寸。视觉请求最多处理一个并保留最新待处理请求，过时观察不积压。

专注委托先只支持时长、学习目标、无关内容持续多久才提醒、提醒方式与冷却几个参数，POC 同时只运行一个专注委托。对话与一个后台操作任务可以继续运行。云端判断证据不足时保持安静；真正提醒前检查委托、页面版本与有效期。提醒触发不能自动打开已关闭的麦克风；语音提醒需要输出通道就绪，否则明确以气泡呈现。

运行期间先记录前台应用变化与已取得的屏幕观察。工作区没有 ActivityWatch 接入代码，因此首版不增加其安装和集成依赖，也不把观察脚本中仅有的前台 App 字段当作完整窗口／网页信息。标题、URL 等仅在确实可取得时写入，睡眠和采集停顿保留空白。

回顾只覆盖 POC 实际开始采集之后的时间；区间起止由记录计算，模型解释这些区间。首版长期记忆只保存用户明确要求保留的偏好与设置，使用作用域区分本次专注和长期偏好。暂不做自动记忆提炼、向量检索或用户画像。

**首轮验收是一段可以完整体验的实际使用过程。** 启动桌宠 → 快捷键对话 → 发起真实计算器任务并继续聊天 → 询问屏幕 → 开启短时专注 → 在学习和无关内容之间切换 → 收到一次合适的提醒 → 取消 → 回顾刚才的时间段。这个过程中的失败直接定位到语音、视觉、执行器或专注模块，修复后重跑相关部分。

通用监控生成与热加载、多 Agent 团队、任意应用兼容、全天自动记忆、完整 ActivityWatch 时间线、跨机器部署、分发打包和精细角色动画都放在这个闭环之后。当前重点是让已经验证的三项能力在一个桌宠里共同工作，并让用户尽早判断这个体验是否值得继续做。
