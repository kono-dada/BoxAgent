# REQ-06：全双工参与判断与静默

状态：设计中，未实现。2026-10-13 用户反馈：开启全双工后，与旁人交谈也会被伙伴当成对它说话。

## 产品目标

全双工表示伙伴具备同时收听和输出的能力，不能意味着附近每句话都要求它回答。默认使用“智能参与”：用户叫它或明确与它互动时进入对话，连续交流无需每句叫名字；转向别人、离开对话或无法确定对象时安静等待。关闭麦克风仍保留为用户直接控制，不作为唯一解决办法。

“你吃饭了吗”“可以”“帮我打开计算器”既可能说给伙伴，也可能说给旁人。只看一句文本、只识别是不是用户的声音，均无法可靠确定对象。第一版必须有明确入口和保守的参与判断，不能宣称能完全自动读懂多人现场。

## 当前链路与缺口

- `QwenRealtimeSession` 的 `speech_started` 会改变当前 Query 并取消回复；任何附近讲话都可能打断伙伴。
- `InteractionService._conversation_event(user_final)` 将每条定稿语音建立为正式 Product Interaction，然后调用 `respond_to_query`。
- `TurnPreparer` 调用 `IntentReference.estimate(query, context=近期正式对话)`，当前参考包含操作、进度询问和普通对话三道独立二选题的概率。它判断内容意图，尚未判断“这句话是否说给伙伴”；现有聊天/任务接收保护不能替代参与判断。
- 生产 AOQ 使用宿主控制 `response.create`，可在生成前决定不创建回复。仅在提示词里要求 silent，或在生成之后调用静默工具，无法保证原生音频播放前拦住输出。

## 推荐交互

| 状态 | 行为 | 进入与离开 |
|---|---|---|
| 安静等待 | 收听参与线索，不抢答，不派任务；窗口显示“安静等待 · 叫我即可” | 开启智能参与后的默认状态；明确呼叫当前角色名字或点击“和我聊”进入对话 |
| 正在对话 | 对与伙伴相关的连续发言自然回应；每轮仍判断对象，短回答结合伙伴上一句问题理解 | 对话停止超过短暂窗口后回到等待；明确转向旁人或参与不确定时本轮静默 |
| 用户要求安静 | 不主动开口，任务结果只在界面显示；已接受任务继续执行 | “先别说话／我在和别人聊”等明确表达进入；明确呼叫或点击恢复后离开，不能仅因超时恢复 |

对话窗口可先以 15 秒作为待验证参数，从伙伴实际播放结束计算，不在后台任务期间无限续期。时间只提供关联线索，不是“窗口内任何声音都可以回复”的许可。用户安静要求优先于窗口。

可在设置里保留“持续对话”选项，适合独处时希望任何发言都得到回应的用户；默认推荐智能参与。麦克风关闭与安静等待用不同状态显示。

## 每轮参与判断

参与判断先于操作意图、记忆召回和正式对话写入，输出 `addressed / not_addressed / uncertain` 及有限的原因类别。可复用当前决策服务基础设施，问题、输入及失败策略必须单独定义，不能用 `p_action` 代替。

输入使用当前发言、角色当前名字、最近少量已接受对话、伙伴是否刚提问、交互时间和用户选择的状态。明确呼叫、界面主动开启是强线索；话题相关只是弱线索。仅“帮我”等字眼、声音属于用户、后台有任务运行，均不足以判定对象。短确认不能脱离上下文分类。没有声纹或多人分离时明确标为缺失信息。

第一版等待状态优先明确呼叫或界面入口；对话状态以语义判断连续回应。不确定、服务失败或超时均保持安静，不反复询问“你是在和我说话吗”。记录可观测原因并支持用户明确纠正。判定置信度与响应率需要标注样本校准，设计阶段不预设已可靠的概率门槛。

## 宿主需要统一执行的边界

1. **回复**：未接受的语音不发 `response.create`，不让静默文本出现在小窗；文本输入仍视为明确发给伙伴。
2. **任务**：仅接受的用户回合可以触发工具或 FIX-03 的承诺补派发。旁人讲话不取消已接受的后台任务；明确取消仍正常处理。
3. **打断**：不能把每次 VAD 直接等同于用户打断。保留真正的全双工打断体验，同时核实 AOQ 对 `interrupt_response` 的支持；若先暂停播放，不能在参与判定前就将原请求终结或丢弃原目标。此项需要真实 AOQ 实验，未证明支持无损暂停/恢复。
4. **通知**：旁人交谈或用户要求安静时，非紧急任务结果只显示在界面，不主动语音插话。是否重新播报应避免过期消息集中播出。
5. **Product Session 与记忆**：未接受的现场讲话不作为正式用户消息，不进入上下文 checkpoint、长期记忆提取或任务历史。诊断默认只存事件 ID、状态与原因，不存未接受的全文。
6. **云端连续上下文**：当前 AOQ 持续上传音频，ASR 定稿前云端已经接收现场声音。自动静默不等于停止上传。需用 provider 的真实 item ID 删除未接受语音项并等待回执，保持已接受对话的连续上下文；同时核实音频项、转写与清理语义。状态丢失或清理失败应停止复用未知上下文，不能把现场讲话积累后重新注入。
7. **输入收尾**：静默分支显式结束候选输入的等待状态，释放准备/投递相关资源，不能依赖一个永远不会产生的 `response_done`。新候选语音不应先关闭已接受的 Interaction。

云端删除只管理后续模型上下文，不代表撤回已上传音频。需要停止收音及上传时使用麦克风关闭；界面应清晰说明安静等待仍开启麦克风。第一版不要求摄像头，也不默认录入旁人的声纹。

## 实施顺序与验收

先验证 AOQ 自动打断控制、未接受语音项删除回执及保持连续对话的协议行为，再接参与状态和决策服务。交互策略落在 application/domain，AOQ/Qwen 只实现协议与播放动作；bootstrap 构造依赖。接上会话、记忆、工具和通知的共同边界后再调界面与判断阈值。

验收至少覆盖：初次明确呼叫、连续回答“可以”、同一用户转向旁人、旁人说操作命令、电视/音乐人声、用户要求安静再呼叫、模型超时、任务运行中旁人聊天、任务结果静默显示、输入插话及丢回执。分别统计旁人误回应、误任务、真实用户漏回应、恢复延迟和正常打断延迟，人工标注交谈对象，不能仅凭工具调用率验收。

硬约束：未接受候选输入不建立正式用户回合，不写长期记忆，不派任务；未知判断静默；不能因旁人交谈终止已接受任务。离线样本和真正多人 AOQ 连续语音均需要验证后才能标记完成。
