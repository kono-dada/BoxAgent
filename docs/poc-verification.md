## 2026-09-19：任务诊断与结束反馈

启动参数 `--log-dir` 控制状态事件和任务诊断的输出目录，默认 `.runtime/pet/`；也可使用已忽略的 `logs/boxagent/`。界面不设日志入口，只显示执行中、等待进展、明确的结束状态、耗时和用户能理解的失败原因。

修复失败工具记录被丢弃的问题：错误步骤现在也能作为失败原因的证据引用，但不能凭全部失败的观察宣称成功。真实故障样本的三个工具调用均返回 `bootstrapTimedOut`，旧版末尾又报证据引用错误，掩盖了连接超时。旧版未保存模型原始最终回复，无法还原其具体引用；本次根据实际错误类型添加了回归用例，并未重新执行用户的应用操作。

新增任务元数据、RPC 起止与耗时、失败工具返回、模型公开回复、异常堆栈、授权、取消、进程退出和最终结果。运行时每 10 秒写入诊断心跳；心跳表示本地执行协程仍在运行，不表示远端有进展。`status.json` 和 `result.json` 原子写入。结构化日志隐藏凭据字段、Bearer 内容与内嵌图片，原始界面文字仍属于本机私有数据。

### 早期 Computer Use 光标残留排查（后续已改动）

用户反馈光标残留后，系统窗口列表实际查到 2 个 `Software Cursor`，均由常驻 `SkyComputerUseService` 持有；此时没有 Computer Use 执行客户端。此前仅凭 App Server 和客户端退出就认为清理完成，遗漏了共享服务的浮层。确认服务空闲后重启该服务，窗口列表读回残留数量为 0。

本机官方客户端的 `--help` 提供 `turn-ended <payload>`，已有 Codex 配置也使用该通知。原退出实现收到模型轮次结束后立即终止 App Server，没有等待结束通知；这可能与通知执行发生竞态，但目前没有日志证明每个残留浮层的具体成因。新增 `thread_id` / `turn_id` 日志用于后续定位。

本次尝试显式等待结束通知，协议单元检查通过，但真实客户端在 5 秒和 20 秒内均未返回；只列出应用的整条连接检查也在 MCP 初始化阶段超时，未执行任何应用操作。因此撤下了未验证有效的通知补丁，正常任务退出逻辑暂时保留原实现，不自动重启共享服务。当时残留已清除。后续已重新加入按任务标识发送通知的实现，详见下方最新复核；自动防止复发仍未获得完整真实验收。

## 并发与取消

`uv run --script scripts/pet.py --check` 的 7 项检查全部通过：等待任务时查询状态仍可响应、关闭语音不取消任务、显式取消不报成功、忙碌时不启动第二个任务、说话不丢失后台状态、插话丢弃旧音频而不取消任务、结果等待用户讲话结束后才回传。

真实执行器启动期间的取消测试在 3.224 秒结束，状态为 `cancelled`。进一步测试在真实任务第 2 次操作（清除按钮点击）已派发时取消，13.070 秒结束，状态为 `cancelled`，操作计数停在 2，子进程已退出。取消先阻止后续派发，再终止后台进程；已经发给系统的操作不回滚。见 取消摘要（本机私有记录：`.runtime/private/artifacts/pet-poc/cancel-summary.json`）。
